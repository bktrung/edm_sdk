Event-driven messaging for Go

A clear path from event to effect.

F1 gives services a broker-agnostic port for publishing and consuming events, with explicit delivery, failure, and shutdown boundaries.

Start with the quickstart See the runtime map
Before you integrate

RabbitMQ is the supported external adapter. In-memory is the deterministic reference and test adapter. Kafka is a scaffold and its Driver.Open returns driver.ErrUnsupported.

Review adapter status and limits

The operating contract

Guarantees with their boundaries attached.

Read each promise with the condition beside it. Source and tests remain the authority for current behavior.

DeliveryAt-least-once with stable identity

F1 preserves an idempotency key across retries, dead-letter copies, and redelivery. Delivery can repeat, so the application owns deduplicating its effects through Event.IdempotencyKey().

Read the guarantee owner

OrderPer-key ordering, not global ordering

OrderedByKey can preserve order for a key across the subscription path. F1 does not promise one global order across partitions or queues.

Read the ordering guide

ShutdownDrain accepted work before exit

A runner stops fetching, settles in-flight deliveries, and can be explicitly drained. Client.Close coordinates runner drain, waits for publishes, flushes, and releases driver resources.

Read the shutdown guide

PriorityFair lanes with bounded waiting

Priority scheduling uses weighted lanes and aging so lower-priority work gets a bounded wait under sustained higher-priority load. The bound is a runtime scheduling property, not a global broker order.

Read scheduling details

What F1 does not claim

  • Exactly-once transport or effects
  • SDK-owned effect deduplication
  • Global ordering
  • Kafka runtime support today
  • A database transaction or outbox

Install, configure, then publish.

The local fixture is for development. Provision production topology separately and disable automatic creation there.

Use the private module

F1 is hosted at fgit.zapps.vn. Set GOPRIVATE=fgit.zapps.vn so the Go toolchain does not use the public proxy or checksum database for this module. The repository pins Go 1.26.1.

Run the safe fixture path

examples/config.yaml uses a local RabbitMQ endpoint, development credentials, and topology.autoCreate: true. Treat those values as fixture-only.

Start, smoke-test, compile, and stop from a clean checkout. Use make broker-down for cleanup. make broker-reset destroys volumes and is not routine cleanup.

Keep service logic on the port.

Publish and handler code use F1 types. Select a concrete driver only at the application composition boundary.

Publish from service code

id, err := client.Publisher().Publish(
    ctx,
    "orders.created.v1",
    OrderCreated{OrderID: order.ID},
    f1.WithKey(order.CustomerID),
)
if err != nil {
    return fmt.Errorf("publish order: %w", err)
}
log.Info("published", "id", id)

The key is routing metadata. It supports per-key ordering when the subscription requests that mode. See publishing events.

Consume and decode

runner, err := client.Subscribe(ctx, f1.Subscription{
    Name: "orders",
    Handlers: map[string]f1.Handler{
        "orders.created.v1": f1.HandlerFunc(
            func(ctx context.Context, event *f1.Event) error {
                var payload OrderCreated
                if err := event.Decode(&payload); err != nil {
                    return f1.Terminal(err)
                }
                return handleOrder(ctx, event.IdempotencyKey(), payload)
            },
        ),
    },
})
if err != nil { return err }
go runner.Run(ctx)

A handler returns nil for success. Use subscriptions and handlers for full configuration. The consumer example shows driver selection separately.

Composition boundary only

client, err := f1.New(ctx, cfg,
    f1.WithDriver(rabbitmq.Driver{}),
)

This is application wiring in main. The root package and business-facing handler path do not import a broker client. Read the import boundary.

Name the outcome before you settle.

Every handler result has a deliberate path. Retry and dead-letter successors are confirmed before the original delivery is acknowledged.

Handler resultF1 actionBoundary
SuccessnilAcknowledge the original delivery.The effect may still be repeated by a later redelivery; use the idempotency key for application-owned safety.
Retryordinary errorPublish the next retry successor using the configured ladder, then acknowledge the original.Retries are bounded by the subscription policy.
RetryRetryAfterUse the explicit delay for that attempt, then follow the same successor-first settlement.The error remains retryable; the delay is not a new delivery guarantee.
TerminalTerminal(err)Publish a dead-letter copy with reason and error, then acknowledge the original.OnDeadLetter is notified only after a confirmed copy.
DropDrop(err)Acknowledge without retaining a dead-letter copy.Use when the application intentionally treats the event as handled without another attempt.
Unmatchedno handlerIgnore acknowledges and discards. DeadLetter retains a copy.Choose Subscription.UnmatchedPolicy explicitly for the event types you route.
1. Classify

Handler outcome, decode failure, or panic becomes an explicit disposition.

2. Confirm successor

Retry or dead-letter publication is durably confirmed by the shared producer.

3. Acknowledge original

The original delivery is settled only after the successor handoff.

This settle-last window prevents loss but permits duplicate delivery or effects if a process crashes after publication and before acknowledgement.

Poison and no-route safety

A poison message can fail decoding or panic in a handler. If bounded successor publication attempts find no dead-letter route, F1 acknowledges and drops the poison message to prevent infinite redelivery, then reports the condition through the configured asynchronous error handler or last-resort logger. That is a containment path, not a retained DLQ copy.

OnDeadLetter receives a confirmed DLQ copy. Terminal callbacks and the client error handler run asynchronously with bounded notification contexts; a slow, panicking, or over-capacity callback can time out or be dropped.

Drain runners, then close.

Publish admission, consumer work, and driver resources have separate lifecycle phases.

  1. Stop admissionClient.Close prevents new work after shutdown begins.
  2. Drain subscriptionsEach Runner.Drain stops fetching and waits for accepted deliveries to settle.
  3. Wait for publishesIn-flight application publishes finish before producer teardown.
  4. Flush and releaseThe producer and connection close with retryable phase handling when a caller deadline expires.

Explicit runner drain

runDone := make(chan error, 1)
go func() { runDone <- runner.Run(ctx) }()

// On SIGTERM:
drainCtx, cancel := context.WithTimeout(
    context.Background(), 20*time.Second,
)
defer cancel()
if err := runner.Drain(drainCtx); err != nil {
    return err
}
return <-runDone

The consumer example owns this signal pattern. Read settlement and shutdown for phase detail.

Choose a port, then inspect its limits.

Adapter status and capability declarations are separate facts. A declared Kafka ceiling does not make an unsupported open path usable.

Client.Limits()

After a successful connection, Client.Limits() reports feature modes for that connected driver: native, emulated, or unavailable. Review the report when a feature depends on transport behavior.

limits := client.Limits()
for _, feature := range limits.Features {
    fmt.Println(feature.Feature, feature.Mode)
}

Capability reading rule

Kafka's Capabilities() describes a planned ceiling across modes. Because Open is unsupported, do not present those values as connected deployment features or demonstrate Client.Limits() against Kafka.
